# 05. 운영 루틴

원문 6.2의 단계별 체크리스트를 실제 일정으로 바꾼 것이다.

---

## 최초 1회 — 설정

### 1. 설치

```bash
git clone <이 저장소>
cd Bitcoin-Core-Strategies
pip install -r requirements.txt
pip install -e .            # btc-core 명령 등록 (선택)
```

`pip install -e .`를 건너뛰면 `python3 -m btc_core.cli` 로 대신 쓸 수 있다.

### 2. 자산 배분 결정

전략을 돌리기 전에 세 통의 크기를 정한다.

- **코어 40%** — 어떤 신호에도 팔지 않을 몫. 기본값이 40%지만 본인 기준으로
  바꿔도 된다. 바꾸면 `config/strategy.yaml`의 `core_hold_pct`와 분배 사다리
  합계를 함께 조정해야 한다(검증이 막아준다)
- **트레이딩 60%** — 분배 사다리가 쓸 몫
- **예비 현금** — 매집 사다리용. 정기 DCA 예산과 **분리**해야 한다

이 숫자를 어딘가에 적어 둔다. 엔진은 비율만 알려주고 금액은 모른다.

### 3. 데이터 받기

```bash
btc-core fetch --save data/market.csv
```

CoinMetrics 커뮤니티 API에서 **전 구간**(2010-07-18 ~)을 받는다. API 키 불필요.

기본값이 전 구간인 이유는 서멀캡 배수 때문이다. 그 지표의 분모는 창세 이래
누적 채굴수익이라, 창을 자르면 분모가 작아져 배수가 부풀려진다. 실측으로
8년 창은 +10.1%, 4년 창은 +84.4% 과대평가됐다. 밸류에이션 계열은 `max_abs`
집계라 부풀려진 값 하나가 30% 지분을 통째로 가져간다.

`--years` 로 창을 줄이면 서멀캡은 **계산되지 않고 결측 처리된다.** 그럴듯한
숫자를 조용히 내주는 것보다 낫다는 판단이다. 200주 이동평균만 필요하다면
5년으로도 되지만, 그 경우 밸류에이션 계열은 MVRV Z·NUPL 두 개로만 돌아간다.

받아 두면 다음부터는 `--csv data/market.csv`로 오프라인 실행이 가능하다.
네트워크가 막힌 환경이면 이 파일을 다른 곳에서 받아 옮겨도 된다.

### 4. 수동 입력 파일 만들기

```bash
btc-core init
```

`data/manual_input.yaml`이 생긴다. BM Pro 차트를 보고 채운다.
[8장의 차트 주소](#부록--차트-바로가기)를 참고.

### 5. 며칠 돌려서 이력 쌓기

```bash
btc-core score --csv data/market.csv
```

**확정 대기 규칙(3일 연속) 때문에 첫날은 어떤 계단도 실행할 수 없다.** 최소
3일 이상 돌려야 사다리가 작동한다. 급할 것 없다 — 사이클은 몇 달 단위다.

## 주 1회 — 15분

가격 계열은 매일 바뀌지만 밴드는 몇 주에 한 번 바뀐다. 주 1회로 충분하다.

```bash
btc-core fetch --save data/market.csv
btc-core score --csv data/market.csv
```

**볼 것 세 가지**

1. **BCS 밴드가 바뀌었나** — 안 바뀌었으면 여기서 끝. 5분이면 된다
2. **`▶` 표시된 실행 가능 계단이 있나** — 있으면 실행하고 `commit`
3. **경고 줄에 뭐가 떴나** — 특히 "고정 앵커와 과거분포가 크게 갈립니다"

> **확정 대기에 관해.** 사다리는 임계 돌파가 `confirm_days`(기본 3일)만큼
> **유지**돼야 열린다. 세는 것은 실행 횟수가 아니라 기간이라, 주 1회로
> 돌려도 두 번째 관측(7일 뒤)에서 확정된다. 처음 돌린 날은 유지 기간이
> 0일이라 반드시 "확정 대기"가 뜨는데, 이건 정상이다 — 하루짜리 스파이크에
> 반응하지 않기 위한 장치다.

계단을 실행했으면 반드시 기록한다.

```bash
btc-core commit --ladder distribute --note "1단 분배, 평단 118,400"
```

## 월 1회 — 40분

원문 6.2의 6단계를 한 번씩 다 밟는 날이다.

### 1. 수동 입력 갱신 (15분)

BM Pro에서 5개 차트를 보고 `data/manual_input.yaml`을 갱신한다.

| 항목 | 차트 | 읽는 법 |
|---|---|---|
| `cvdd` | `/charts/cvdd/` | CVDD 선의 현재 달러값 |
| `lth_rp` | 위와 같은 차트 | LTH 실현가격의 현재 달러값 |

`as_of` 날짜를 반드시 오늘로 고친다. 안 고치면 45일 뒤 경고가 뜨고 120일 뒤
자동으로 결측 처리된다.

### 2. 거시 갱신 (10분)

| 항목 | 차트 |
|---|---|
| `m2_impulse` | `/bitcoin-macro/m2-global-vs-btc/` |
| `dxy_trend` | `/bitcoin-portfolio/btc-vs-dxy/` |
| `fed_stance` | `/bitcoin-macro/fed-balance-sheet-vs-btc/` + 최근 FOMC |
| `etf_flow` | ETF 순유입 추적 사이트 |

### 3. 스냅샷 저장 (5분)

```bash
btc-core score --csv data/market.csv --format markdown \
  --out journal/2026-07.md
```

마크다운 리포트 끝에는 빈칸이 붙어 나온다.

```markdown
### 이번 판단 기록 (직접 채울 것)

- 무엇을 근거로 어떻게 판단했나:
- 실제로 실행한 것:
- 이 판단이 틀렸다면 무엇 때문일 것 같은가:
```

### 4. 기록을 채운다 (10분)

**이 단계가 이 루틴에서 가장 중요하다.** 원문 6.4가 그렇게 말한다.

> 다음 사이클에서 같은 지표를 볼 때, 자신이 어디서 틀렸는지 아는 것이 지표
> 자체보다 더 큰 자산이 됩니다.

세 번째 질문 — "이 판단이 틀렸다면 무엇 때문일 것 같은가" — 을 특히 성실하게
채운다. 나중에 이 문장을 다시 읽는 것이 앵커를 고칠 때 가장 유용한 자료가 된다.

## 분기 1회 — 1시간

### 앵커 점검

지난 3개월 리포트에서 "고정 앵커와 과거분포가 크게 갈립니다" 경고가 몇 번
떴는지 센다.

- **0~1회** — 정상
- **2~4회** — 주시
- **5회 이상** — 해당 지표의 앵커를 조정할 때다

조정할 때는 `config/strategy.yaml`의 앵커 좌표를 고치고, **왜 고쳤는지를 저널에
적는다.** 나중에 "이 숫자가 왜 이렇지"를 다시 묻지 않기 위해서다.

### 반증 조건 점검

`config/strategy.yaml`의 `invalidation` 4개 항목을 소리 내어 읽는다.

| ID | 조건 | 발동 시 |
|---|---|---|
| INV-1 | 한 사이클 내내 BCS +70에 못 가고 −45로 내려감 | 상단 앵커 전면 재조정 |
| INV-2 | BCS −70에서 매집 후 2년 지나도 원가 미회복 | 전략 중단 후 재설계 |
| INV-3 | 가격 계열이 나머지 3계열과 두 사이클 연속 반대 | 가격 계열 가중치 0 |
| INV-4 | ETF 유입이 온체인을 6개월 이상 무력화 | LRS를 BCS 계열로 승격 검토 |

**하나라도 걸렸으면 전략을 고치는 게 아니라 멈추고 다시 설계한다.** 반증 조건을
미리 적어 두는 이유는, 사후에 합리화하지 않기 위해서다.

## 사이클 1회 — 반나절

BCS가 +70을 찍었다가 −45 아래로 내려온 뒤, 즉 한 사이클이 끝난 뒤.

1. 저널 전체를 시간순으로 읽는다
2. 각 판단이 **그때 알 수 있었던 정보로** 합리적이었는지 따져본다 (결과가 아니라
   과정을 본다)
3. 앵커·가중치·사다리 간격을 조정한다
4. 조정 이유를 저널에 남긴다
5. `data/state.json`은 지우지 않는다 — 재무장 규칙이 알아서 다음 사이클을 준비한다

## 언제 이 시스템을 무시해야 하나

**개인 사정이 시장보다 우선일 때.** BCS가 −80이어도 6개월 안에 쓸 돈이면 넣지
않는다. 원문 7.4의 마지막 문장이 이것이다.

> 확률이 유리한 쪽에 서는 도구로 쓰되, 자신이 감당할 수 있는 범위를 넘어서는
> 판단의 근거로 삼지 마세요.

**커버리지가 60% 미만일 때.** 엔진이 알아서 사다리를 잠그지만, 그 상태가 오래
가면 데이터를 고칠 때지 그대로 굴릴 때가 아니다.

**계열이 서로 갈릴 때.** 리포트에 "계열 충돌"이 뜨면 판단 보류가 정답일 확률이
높다. 억지로 방향을 정하지 않는다.
